SUITE 04 / ABOUT

The test is part of the work.

I graduated with a BSc in Information Technology from North-West University in 2024 and started working as a graduate software engineer in October 2025.

What QA taught me

A bug report is a starting point, not a diagnosis. I try to reproduce the behaviour, write down what is confirmed and what is only a theory, then test the fix against the original case. It saves me from treating a plausible explanation as a fact.

My professional work has included .NET backend changes and Angular frontend work. Employer details stay out of this site apart from a plain experience entry in my CV.

Using AI without handing it the keys

I use AI tools to help understand unfamiliar code, explore test cases, review a change and draft explanations. They can be useful at finding a question I had not thought to ask.

They can also invent files, skip a condition or sound certain without evidence. I check the output against the code, and I am working on relying less on generated logic when I should be able to explain the solution myself.

ILLUSTRATIVE OUTPUT FORMAT / NOT AI TOOL OUTPUT

01 / Issue in plain language

The saved invoice note may not be reflected immediately on the detail page.

02 / Confirmed vs suspected

Confirmed from the synthetic report: the issue is intermittent and concerns a stale note after saving. Not confirmed: the cause, browser, request response, caching behaviour or reproduction steps.

03 / Missing details

Ask for repeatable steps, browser and version, the response after saving, whether a reload changes the note, and whether the issue affects one or several invoices.

04 / Fixes ranked by risk

Do not change code yet. First capture the save request and subsequent read, then reproduce with a controlled example. Any implementation change depends on that evidence.

05 / Acceptance criteria and tests

After saving a changed note, the displayed value matches the saved value. Test immediate save, reload, repeated edits, slow response and a failed save.
