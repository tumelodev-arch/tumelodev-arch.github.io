FIELD NOTE 001 / DEBUGGING

A failing build is evidence, not a diagnosis.

A working note on pipeline failures.

A failed pipeline is a useful signal, but it is not yet an explanation. The failing step narrows the search. It does not, by itself, prove that the code change caused the failure.

I try to separate a few possibilities: an application or test failure, a dependency or environment issue, a configuration difference, or a problem in the pipeline itself. The first useful action is to inspect the failing step and compare it with a run that behaved differently.

What I check first

  • The exact failing command and its output.
  • Whether the failure is repeatable.
  • What changed between the failing and successful runs.
  • Whether the environment or dependencies differ.

Sometimes the evidence points to the code. Sometimes it points elsewhere. If I cannot prove the cause yet, I should say that and keep investigating rather than make a change that only hides the symptom.

Working rule: record the failing observation first, then the explanation. They are not the same thing.

FIELD NOTE 002 / APPLICATION DESIGN

Validation is part of the domain.

Why rules need to be explicit and testable.

Checking whether a value has the right shape is only one part of validation. A value can be well formed and still be invalid for the operation being requested.

Before writing a check, I find it useful to describe the rule in plain language: which input does it depend on, when does it apply, what makes it fail, and what should the caller be told? That gives the implementation and its test a common point of reference.

Keep the rule reviewable

A clear rule should have a named purpose, a condition that can be tested and a response that helps a caller correct the request. Where the domain has exceptions, those exceptions need evidence and tests too.

For public examples, I use invented records and generic domains. A portfolio project should teach the pattern without copying a real employer's business rule.

Working rule: write the expected behaviour before writing the check.

FIELD NOTE 003 / INVESTIGATION

Write down what would disprove the hypothesis.

A small guard against confirmation bias.

When one explanation looks plausible, it is easy to keep collecting evidence that supports it. I want to ask one more question: what result would make me abandon this theory?

A second example, a focused negative test, or a comparison between environments can expose a gap in the original explanation. If it does, that is useful progress. The investigation became more accurate even if the fix is not closer yet.

Turn the hypothesis into a check

Write down what you expect to observe if the explanation is correct. Then identify one check that could produce a different result. A useful investigation should give the hypothesis a chance to fail.

The aim is not to sound certain. It is to make the next step easier for the person who has to investigate after me.

Working rule: choose the next test for what it can rule out, not just what it can confirm.
