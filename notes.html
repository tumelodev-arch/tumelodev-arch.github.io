NOTES / WORKING IDEAS

Small observations from working with software.

These are short notes, not tutorials. I use them to record a question, the evidence I would look for, and what I still do not know.

FIELD NOTE 001 / DEBUGGING

A failing build is evidence, not a diagnosis.

A working note on pipeline failures.

A failed pipeline is a useful signal, but it is not yet an explanation. The failing step narrows the search. It does not, on its own, say that the code change caused the failure.

I try to separate a few possibilities: an application or test failure, a dependency or environment issue, a configuration difference, or a problem in the pipeline itself. The first useful action is to inspect the failing step and compare it with a run that behaved differently.

What I check first

  1. Can I reproduce the failure, and does it happen consistently?
  2. Is the failure tied to a changed line, a test assertion, a missing dependency, or environment setup?
  3. What changed between a passing run and this run?
  4. What evidence would show that my first theory is wrong?

Sometimes the evidence points to the code. Sometimes it points elsewhere. If I cannot prove the cause yet, I should say that and keep investigating rather than make a fix that only makes the symptom disappear.

Working rule: record the failing observation first, then the explanation. They are not the same thing.

FIELD NOTE 002 / APPLICATION DESIGN

Validation is part of the domain.

Why I want rules to be explicit and testable.

Checking whether a value has the right shape is only one part of validation. A value can be well-formed and still be invalid for the operation being requested.

I find it useful to describe a rule in plain language before writing the check: which input does it depend on, when does it apply, what makes it fail, and what should the caller be told? That gives the implementation and the test a common point of reference.

For public examples, I use synthetic records and generic domains. A portfolio demo should teach the pattern without copying a real employer's business rule.

FIELD NOTE 003 / INVESTIGATION

Write down what would disprove the hypothesis.

A small guard against confirmation bias.

When one explanation looks plausible, it is easy to keep collecting evidence that supports it. I want to ask one more question: what result would make me abandon this theory?

A second example, a focused negative test, or a comparison between environments can expose a gap in the original explanation. If it does, that is useful progress. It means the investigation is more accurate, even if the fix is not closer yet.

The aim is not to sound certain. It is to make the next step easier for the person who has to investigate after me.
