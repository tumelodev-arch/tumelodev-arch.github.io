02 / VALIDATION & DOMAIN LOGIC

Make business rules explicit

Translate requirements into validation that is understandable, testable, and appropriate to the application.

CORRECTNESS

The engineering challenge

Input can be syntactically valid and still violate a business constraint. These cases need deliberate rules, useful feedback, and tests that exercise boundaries.

How I approach it

  • Clarify the expected rule and the invalid states it must prevent.
  • Keep validation near the relevant application boundary.
  • Consider negative and boundary cases, not just successful input.
  • Use test results to verify the rule behaves as intended.

What this demonstrates

Practical experience implementing custom validators, investigating edge cases, and making the reason for a rejection easier to identify. The original employer-specific rule is intentionally not reproduced here.

03 / TEST AUTOMATION

Test the journey, not just the component

Use repeatable end-to-end checks to exercise important user flows and help catch regressions.

QUALITY

The engineering challenge

A feature can work in isolation but fail when connected to navigation, persisted data, calculations, or other parts of the workflow.

How I contribute

  • Build Cypress end-to-end specs aligned with defined test plans.
  • Exercise key journey steps and verify visible or persisted results where appropriate.
  • Use focused negative tests during defect investigation.
  • Review failures carefully rather than assuming every failure has the same cause.

What this is building

Stronger quality habits: test design around user behavior, more deliberate regression thinking, and clearer evidence when a change succeeds or fails.

04 / DEBUGGING & DIAGNOSIS

Follow the evidence before the fix

Reproduce a problem, narrow the possibilities, and be precise about what the evidence does—and does not—prove.

INVESTIGATION

The engineering challenge

Reported failures may have incomplete steps, multiple examples, different environment behavior, or symptoms that look similar but have different causes.

My investigation habits

  • Reproduce the reported behavior when possible.
  • Inspect relevant code paths, logs, and environment differences.
  • Compare examples and use targeted negative tests to challenge a hypothesis.
  • Record unresolved questions instead of overstating certainty.

Why it matters

Disciplined debugging reduces guesswork, supports better collaboration, and makes it easier to distinguish an application issue from a pipeline or environment issue.
